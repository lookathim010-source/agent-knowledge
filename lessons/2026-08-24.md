# Lessons — 2026-08-24

- **Structure Claude Code fleet automation around its loop primitives: goal-based loops that iterate until a measurable, deterministic condition passes, and time-based loops (/loop, /schedule) for recurring monitoring — Osmani runs 5–10 parallel agents this way under a four-tier taxonomy (agentic, goal-based, time-based, proactive).**
  - Why it matters here: This is the CCCLI fleet pattern named and field-tested at 80k-repo scale; the daily-dev learn loop itself is a time-based loop, and IPI-Engine promotion gates fit goal-based loops ('iterate until DSR criterion passes').
  - Do: Define each fleet job as goal-based (measurable finish line) or time-based (cadence) before writing its prompt.

- **Run agent fleets like a software factory: triage labels, explicit handoff protocols, a per-run verification budget, a run-status taxonomy (success / flawed / blocked / manual), and sandboxing for untrusted inputs — human judgment relocates to product intent, architecture, quality bar, and risk.**
  - Why it matters here: Maps 1:1 onto the evidence-gated CCCLI doctrine; the run-status taxonomy is a ready-made vocabulary for fleet reports and matches the existing blocked-vs-failed rule.
  - Do: Adopt success/flawed/blocked/manual as the standard verdict field in every fleet run report.

- **At agent code volume, enforce quality through gates built into the harness and pipeline — unit/property/mutation tests, complexity metrics, lint-enforced architecture rules, compiler/CI back-pressure applied throughout the loop — not through human review at the end.**
  - Why it matters here: Second independent source in two days pointing the same way as the custom-linters lesson (2026-08-23): deterministic gates beat LLM review for scale; reserve human judgment for subjective calls.
  - Do: Add mutation testing and complexity ceilings to the CCCLI quality-gate list.
